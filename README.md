# Spotty

Модульный терминал-монитор портов. Кроссплатформенное десктопное приложение на C++20 и
Qt 6, в котором плагинами добавляются и транспорты, и панели.

**Версия:** 0.3.0a · **Состояние:** все этапы завершены

---

## Что это

Программа для работы с последовательными портами и другими потоковыми интерфейсами:
смотреть вывод устройства, отправлять команды, вести логи, гонять макросы. Отличие от
десятков похожих утилит — в том, что новый транспорт (TCP, CAN, Bluetooth SPP, воспроизведение
файла) добавляется отдельным плагином, не трогая ядро.

Главная цель версии 0.3.0a — не набор функций, а **проверка API плагинов на прочность**.
Если API спроектирован верно, следующий транспорт добавляется без правок ядра. Ради этой
проверки первым написан не UART, а искусственный плагин `loopback`: если SDK удобно ложится
на транспорт, устроенный совсем иначе, значит он не выродился в «интерфейс к UART под
другим именем».

Та же проверка проведена и со вторым видом плагинов. Макросы, логирование, поиск и
генератор — не встроенные панели, а обычные загружаемые модули, ничем не отличающиеся от
сторонних. Проверить это можно, убрав любой из них из каталога плагинов: приложение
запустится без него и без единого следа в коде.

## Состояние по этапам

| Этап | Содержание | Состояние |
|---|---|---|
| 1 | Каркас, ядро, SDK плагинов, темы, плагин `loopback` | **готово** |
| 2 | Плагин UART, разборщик ANSI, пакетизация, настоящий терминал | **готово** |
| 3 | Панели: макросы, логирование, поиск, генератор | **готово** |
| 4 | Диалог настроек, локализация ru/en | **готово** |
| 5 | Тесты, CI, упаковка | **готово** |
| 6 | Второй SDK: панели и обработка данных плагинами | **готово** |

### Что работает сейчас

- Плагины загружаются **двумя способами**: как отдельные модули и вкомпилированными
  в исполняемый файл. Оба режима проверены.
- **UART** поверх Qt SerialPort: перечисление по VID/PID, управление DTR/RTS/BREAK,
  индикация линий CTS/DSR/DCD/RI, перенастройка на лету.
- **Терминал** с разбором ANSI (SGR, цвета 16/256/truecolor, управление строкой), метками
  времени, разделением приёма и передачи, HEX-дампом, умным автоскроллом, выделением и
  копированием.
- **Пакетизация** приёма: по переводам строк, по межбайтовой паузе, по разделителю, по
  фиксированной длине.
- **Панели плагинами**: макросы с горячими клавишами и повторной отправкой, логирование с
  перетаскиванием файлов, поиск с фильтром и правилами подсветки, генератор посылок — все
  четыре загружаются как обычные модули. Плюс два примера: график из CSV поверх терминала
  и отправка файла с перекодированием в base64.
- **Обработка данных**: цепочка фильтров, через которую плагин может изменить или
  проглотить байты до того, как их увидит терминал.
- **Настройки**: шесть разделов, включая палитру ANSI и назначение горячих клавиш.
- **Локализация** ru/en, тёмная и светлая темы, единственный экземпляр приложения.

- **264 модульных теста** на GoogleTest, непрерывная интеграция на пяти конфигурациях,
  сборка распространяемых пакетов.

### Чего ещё нет

Всё запланированное на 0.3.0a сделано. Отложенное на следующие версии: CRC и контрольные
суммы в отправке, ротация и экспорт логов, воспроизведение лога с исходными таймингами.

## Сборка

### Требования

- CMake 3.21 или новее
- Компилятор с поддержкой C++20 (GCC 11+, Clang 14+, MSVC 2022)
- Qt 6.5 или новее: `Core`, `Gui`, `Widgets`, `Network`
- Необязательно: `Qt6::SerialPort` — без него не собирается плагин UART
- Необязательно: `Qt6::LinguistTools` (`qttools`) — без них интерфейс останется английским
- Необязательно: `qttranslations` — переводы стандартных строк Qt («ОК», «Отмена»)

Отсутствие необязательных компонентов не ломает сборку: получится урезанный, но рабочий
комплект.

### macOS

```bash
brew install qt qttools qttranslations cmake ninja
cmake -S . -B build -G Ninja -DCMAKE_PREFIX_PATH=/opt/homebrew
cmake --build build
open build/spotty.app
```

### Linux

```bash
sudo apt install qt6-base-dev libqt6serialport6-dev qt6-tools-dev cmake ninja-build
cmake -S . -B build -G Ninja
cmake --build build
./build/spotty
```

### Windows

```powershell
cmake -S . -B build -G Ninja -DCMAKE_PREFIX_PATH=C:/Qt/6.11.1/msvc2022_64
cmake --build build
.\build\spotty.exe
```

### Параметры сборки

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `SPOTTY_STATIC_PLUGINS` | `OFF` | Вкомпилировать плагины в исполняемый файл вместо загрузки во время работы |
| `SPOTTY_BUILD_TESTS` | `OFF` | Собрать модульные тесты |
| `SPOTTY_ENABLE_COVERAGE` | `OFF` | Инструментировать `spotty-core` и `spotty-api` для анализа покрытия |
| `SPOTTY_GTEST_TAG` | `v1.15.2` | Версия GoogleTest, если системного пакета нет |
| `SPOTTY_COVERAGE_MINIMUM` | `80.0` | Нижний порог покрытия по строкам, % |

### Разработка в VS Code

В репозитории лежат готовые профили: `.vscode/launch.json` и `.vscode/tasks.json`.
Нужны расширения `ms-vscode.cpptools` и `ms-vscode.cmake-tools` — VS Code предложит их
сам при открытии папки.

Отладочная сборка живёт в отдельном каталоге `build-debug`: у неё другие флаги, и
переключение типа сборки в одном каталоге каждый раз обесценивало бы кэш объектных файлов.

### Профили отладки (F5)

| Профиль | Для чего |
|---|---|
| Spotty: отладка | Обычный запуск с включённым журналом `spotty.*` |
| Spotty: без журнала | То же без журнала — когда отлаживается отрисовка |
| Spotty: статические плагины | Вторая половина гибридной сборки |
| Тесты: все | Весь набор под отладчиком |
| Тесты: выбранные | Спросит образец `--gtest_filter`, например `Session.*` |
| Spotty: присоединиться к процессу | К уже запущенной программе |

### Задачи

Имена короткие, потому что выводятся значками в строке состояния (расширение
`actboy168.tasks`). Что делает задача, написано в её описании — оно видно в списке
`Run Task` и во всплывающей подсказке.

| Задача | Что делает |
|---|---|
| `build` | Отладочная сборка; она же по Cmd+Shift+B |
| `static` | Сборка с вкомпилированными плагинами — вторая половина гибрида |
| `test` | Прогон всех тестов |
| `cov` | Тесты с измерением покрытия |
| `i18n` | `lupdate` и заполнение словаря переводов |
| `dist` | Распространяемый комплект |
| `reset` | Удалить настройки Spotty |

`reset` нужен, чтобы проверить поведение при первом запуске: иначе это невозможно,
программа помнит слишком много. Она единственная выделена цветом — стирает данные.

Задачи настройки (`cfg`, `cfg:rel`) и обычная сборка (`build:rel`) из строки состояния
скрыты: первые две — зависимости, а не то, что нажимают руками.

## Тесты

```bash
cmake -S . -B build -G Ninja -DCMAKE_PREFIX_PATH=/opt/homebrew -DSPOTTY_BUILD_TESTS=ON
cmake --build build
ctest --test-dir build --output-on-failure
```

Наборов два, 264 теста.

`spotty-tests` покрывает `spotty-core` и `spotty-api`: разбор ANSI, буфер терминала,
пакетизацию, цепочку фильтров, кодирование данных, хранилища настроек, макросов, истории и
логов, реестр интерфейсов и сессию с поддельным плагином, ограничение на один экземпляр.
Он не линкуется с `Qt6::Widgets` — именно на этом держится гарантия, что вся логика
проверяема без `QApplication`. Графическая подсистема не нужна.

`spotty-ui-tests` покрывает панельный SDK: реестр панельных плагинов, две фазы загрузки,
разбор CSV в плагине графика. Он линкуется с виджетами и запускается под
`QT_QPA_PLATFORM=offscreen`, поэтому тоже работает в контейнере.

GoogleTest берётся из системы, а при её отсутствии скачивается FetchContent по
закреплённому тегу.

### Покрытие

```bash
cmake -S . -B build-cov -G Ninja -DCMAKE_PREFIX_PATH=/opt/homebrew \
      -DCMAKE_BUILD_TYPE=Debug -DSPOTTY_BUILD_TESTS=ON -DSPOTTY_ENABLE_COVERAGE=ON
cmake --build build-cov --target coverage
```

Цель прогоняет тесты, печатает сводку, кладёт подробный отчёт в
`build-cov/coverage/html/index.html` и завершается с ошибкой, если покрытие по строкам
упало ниже `SPOTTY_COVERAGE_MINIMUM`.

Текущее покрытие `spotty-core` и `spotty-api`: **83.9% по строкам**, 79.8% по функциям,
72.1% по ветвлениям. `spotty-ui-tests` в подсчёт не входит: там мерялась бы доля покрытого
кода интерфейса, а он проверяется запуском, а не модульными тестами.

Сборка с покрытием форсит `SPOTTY_STATIC_PLUGINS=ON`: счётчики в разделяемой библиотеке
ведут собственный набор данных профилирования, и сводка по бинарнику тестов их не видит.

Порог существует не ради красивой цифры, а чтобы поймать момент, когда в ядро добавили
код и забыли тест. Стопроцентное покрытие целью не ставится: доводить до него обычно
значит писать тесты на обработчики ошибок файловой системы, которые всё равно не
воспроизвести.

Измеряется только `spotty-core`. Смысла мерить покрытие тестов самими собой нет, а UI и
плагины модульными тестами не покрываются — они проверяются запуском.

Под Clang используются `llvm-profdata` и `llvm-cov`, под GCC — `gcovr`. Сборка ведётся
без оптимизации: с ней строки сливаются и переставляются, и отчёт перестаёт
соответствовать исходному тексту.

### Пакет для распространения

```bash
cmake -S . -B build-pkg -G Ninja -DCMAKE_PREFIX_PATH=/opt/homebrew -DSPOTTY_STATIC_PLUGINS=ON
cmake --build build-pkg --target spotty-package
```

Результат в `build-pkg/package/`: образ `.dmg` на macOS, архив с библиотеками Qt на
Windows, образ `.AppImage` на Linux. Плагины вкомпилированы внутрь — один самодостаточный
файл проще распространять, а несовпадение версии Qt между приложением и загружаемым
плагином становится невозможным по построению.

> **macOS:** подпись ставится ad-hoc, этого достаточно для запуска на своей машине. Для
> раздачи другим нужны Developer ID и нотаризация — скачавший образ с GitHub увидит
> предупреждение Gatekeeper о неизвестном разработчике.

Тот же пакет CI собирает сама и публикует релизом на GitHub — по тегу вида `v0.3.0a`:

```bash
git tag v0.3.0a
git push origin v0.3.0a
```

Джобы `package` (все три платформы) и `release` в `.github/workflows/ci.yml` запускаются
только на такой тег и только после того, как `build` пройдёт на всех платформах. Публикация
идёт сразу, без черновика — откатить можно вручную со страницы Releases.

Статическая сборка нужна для релизов и подписи под macOS, где один самодостаточный
двоичный файл проще в распространении:

```bash
cmake -S . -B build-static -G Ninja -DCMAKE_PREFIX_PATH=/opt/homebrew -DSPOTTY_STATIC_PLUGINS=ON
cmake --build build-static
```

## Запуск и проверка

Проверить работу без единого подключённого устройства позволяет плагин `loopback`. Он даёт
два виртуальных интерфейса: `loopback0` возвращает отправленное, `loopback1` сам выдаёт
поток строк с последовательностями ANSI.

Подробный журнал:

```bash
QT_LOGGING_RULES="spotty.*=true" ./build/spotty.app/Contents/MacOS/spotty
```

Категории журналирования: `spotty.paths`, `spotty.files`, `spotty.settings`,
`spotty.plugins`, `spotty.plugins.jlinkrtt`, `spotty.registry`, `spotty.session`,
`spotty.icons`, `spotty.history`, `spotty.log`, `spotty.macros`, `spotty.instance`.

С настоящим железом:

```bash
ls /dev/cu.*                                  # macOS: найти порт
ls /dev/ttyUSB* /dev/ttyACM*                  # Linux
socat -d -d pty,raw,echo=0 pty,raw,echo=0     # пара виртуальных портов для двусторонней проверки
```

## Файлы конфигурации

Всё хранится читаемым JSON, который можно править руками и класть в систему контроля
версий.

| Файл | Содержимое |
|---|---|
| `settings.json` | Общие настройки: тема, геометрия окна, выбранный интерфейс |
| `interfaces.json` | По устройству: псевдоним, настройки, системное имя |
| `history.txt` | История строки отправки (этап 2) |
| `macros/*.json` | Пресеты макросов, по файлу на пресет (этап 3) |

Расположение каталога:

| Система | Путь |
|---|---|
| macOS | `~/Library/Preferences/Spotty/Spotty` |
| Linux | `~/.config/Spotty/Spotty` |
| Windows | `%APPDATA%\Spotty\Spotty` |

### Переносной режим

Положите пустой файл `spotty-portable.txt` рядом с исполняемым файлом (на macOS — рядом с
`.app`), и вся конфигурация переедет в каталог `config` рядом с ним. Логи по умолчанию тоже
переедут в соседний `logs`. Так весь комплект целиком живёт на флешке.

### Дополнительные каталоги плагинов

Переменная окружения `SPOTTY_PLUGIN_PATH` (разделитель `:`, в Windows `;`) добавляет
каталоги поиска с наивысшим приоритетом. Плагин из пользовательского каталога перекрывает
штатный с тем же идентификатором — удобно при отладке.

### Правила слоёв

Они не формальность — на них держится модульность.

1. **`spotty-core` не линкуется с `Qt6::Widgets`.** Это механическая гарантия того, что
   буфер терминала, разборщик ANSI и пакетизатор останутся проверяемыми без
   `QApplication`, а зависимости от UI не прорастут в модель незаметно.
2. **Никакой плагин не линкуется со `spotty-core`.** Если плагину чего-то не хватает,
   значит этого не хватает в публичном SDK, и добавлять нужно туда.
3. **Плагин интерфейса линкуется только со `Spotty::Api` и виджетов не создаёт.** Он
   возвращает `SettingsSchema`, а диалог настроек строит ядро. Транспорт работает в
   отдельном потоке, где виджеты не только не нужны, но и запрещены.
4. **Плагин панели линкуется со `Spotty::UiApi` и виджеты создаёт** — это его работа.
   Всё, что даёт ему приложение, приходит через `IPanelHost`: ни сессии, ни хранилища
   настроек, ни виджета терминала он не видит.

Граница между двумя SDK проходит ровно по `Qt6::Widgets`. Один SDK на оба вида означал бы
виджеты в зависимостях UART.

### Почему SDK — разделяемая библиотека

`IInterfaceChannel` — класс с `Q_OBJECT`, а Qt сопоставляет сигналы и слоты, сравнивая
**указатели** на `QMetaObject`. Если бы приложение и каждый плагин несли собственную копию
`staticMetaObject`, то `connect()` из приложения к сигналу канала, созданного плагином,
**молча не сработал бы**: ни ошибки сборки, ни предупреждения — просто не приходили бы
данные.

Поэтому `libspotty-api` разделяемая: метаобъект, таблица виртуальных функций и typeinfo
существуют ровно в одном экземпляре. При `SPOTTY_STATIC_PLUGINS=ON` всё собирается в один
двоичный файл, делить нечего, и библиотека становится статической.
